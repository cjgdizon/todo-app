# To-Do app

Production-grade to-do app: Next.js PWA + Expo mobile, Supabase backend (Postgres, Auth, Realtime, Edge Functions), opt-in Google Calendar sync. Full plan: `C:\Users\Cj\.claude\plans\i-want-to-build-virtual-quilt.md`.

## Layout
- `apps/web` Next.js (App Router), `apps/mobile` Expo
- `packages/core` pure TypeScript domain logic (Zod schemas, recurrence, NLP quick-add parser, ordering, filters, task↔calendar-event mapping). No I/O, no framework imports.
- `packages/data` generated DB types (`database.types.ts`), Zod row parsers (`models.ts`), typed queries, TanStack Query hooks with optimistic updates, the offline write queue (`offline-fetch.ts`), and the pieces web and mobile share (`views.ts` view selection, `format.ts`, `recurrence-text.ts`, `persist-codec.ts`). Takes a Supabase client as input and never reads env itself.
- `packages/ui-tokens` design tokens shared by web and mobile. `tokens.ts` is the source; `tokens.css` is generated (`pnpm --filter @todo/ui-tokens generate`) and a test fails if it is stale. A test also checks WCAG AA contrast for every pair.
- `supabase/` migrations, RLS, seed, Edge Functions

## Design
- Read `DESIGN.md` (calm minimal direction, tokens, motion, a11y) before writing any UI.

## Conventions
- Domain logic only in `packages/core`; components and Edge Functions call it, never reimplement it.
- TDD: failing test first (`/ecc:tdd-workflow`). Core coverage target 90%+, overall 80%+.
- Strict TypeScript, no `any`, no `console.log` in `packages/core`. Validate all external input with Zod.
- Every table has RLS keyed on workspace membership. Run the Supabase advisors after each migration.
- Migrations: edit in place only while they have never been applied to a hosted database. After that, add a new migration file; never rewrite an applied one. **The first three migrations were applied to the hosted `todo-app` project on 2026-10-20, so every schema change from now on is a new file.** Hosted versions are timestamped at apply time, so they differ from the local filenames; run `supabase migration repair` once if the CLI is adopted. After a migration, regenerate `packages/data/src/database.types.ts`.
- Synced tables are soft-deleted (`deleted_at`) and have no DELETE policy; `private.purge_deleted()` removes old tombstones. Clients cannot set `version`, timestamps or `updated_by` (the `sync_columns` trigger owns them). Order lists by `position, id`.
- Nobody is added to a workspace by a client insert (no policy on purpose): members join through the server-side invite flow. Ownership changes only via `transfer_workspace()`; a project moves workspaces only via `move_project()`.
- Account deletion must delete or transfer owned workspaces first (`workspaces.owner_id` is RESTRICT); authorship columns become NULL so shared work survives. The flow (M7): `account_deletion_blockers()` lists the shared workspaces the person still owns (they hand each over with `transfer_workspace`, "Make owner" in Members); the `delete-account` Edge Function (verified login + the exact typed words "delete my account", 409 while blockers remain) then does the Google cleanup, deletes their unshared workspaces (`delete_owned_workspaces`), deletes the login (`auth.admin.deleteUser`) and finally removes their files from Storage (best effort; a failure leaves orphaned files, never a half-deleted account). UI: Settings (web) and the More tab (mobile). `node scripts/account-check/check.mjs` runs the whole thing against the local stack.
- Policy helpers live in the `private` schema and are used as `workspace_id in (select private.my_workspace_ids())`.
- `packages/core` uses explicit `.ts` extensions in relative imports so Deno (Edge Functions) can import it; apps import subpaths like `@todo/core/recurrence` when they need only part of it.
- Recurrence rules are untrusted input: only FREQ, INTERVAL (capped per frequency), BYDAY, BYMONTHDAY, BYMONTH, BYSETPOS, UNTIL and WKST are accepted (`validateRrule`), and searches are bounded. Never call `rrule` directly; go through `recurrence.ts`. Import `rrule` only via `rrule-compat.ts` (its named export is missing in plain Node/Deno).
- `packages/core` uses erasable TypeScript syntax only (no enums, namespaces or constructor parameter properties) so Node and Deno can run it; `esm-compat.test.ts` loads it in a plain Node process.
- Time zones are IANA names (`Asia/Manila`, `UTC`), validated by trigger in the database and by luxon in core. Text columns have length caps; add one to any new free-text column.
- Attachment files live under `<task_id>/...` (enforced by a CHECK). `anon` has no table privileges; `authenticated` has no TRUNCATE/REFERENCES/TRIGGER.
- DB tests (`packages/db-tests`) run migrations in PGlite; they do not replace running the advisors and a smoke test on the hosted project.
- Web (Next 16, `cacheComponents` on): layouts stay static. The session is read in the browser by `components/providers.tsx`; `src/proxy.ts` is only an early redirect, and row-level security is the real gate. Never read `cookies()` in a layout. `apps/web/AGENTS.md` says to read `node_modules/next/dist/docs/` before using a Next API.
- E2E: `pnpm --filter @todo/web e2e` (Playwright + axe accessibility scans, Chromium). Needs `pnpm db:start`; it starts the server itself (never reuses a running one: a running build may point at the hosted project), signs up throwaway users through the real form, and refuses to run unless the Supabase URL is local. `.github/workflows/e2e.yml` runs it on every push and PR against a local Supabase, with `E2E_SERVER=start` (production build). Reload only via `reloadWhenSaved`, never right after a write. Unit tests are `src/**/*.test.ts`; the `e2e/` folder is excluded from Vitest.
- Next keeps pages you visited earlier mounted but hidden. Never rely on a fixed element `id` or `getElementById` for per-page UI (use `useId` and a visible-element lookup like `focusQuickAdd`), and scope Playwright locators to visible elements (`taskRows`, `getByRole`). The `(app)` group sets `export const instant = false` because its content only renders once the browser session is known.
- Import/export (`@todo/core` `exchange.ts`, `import-plan.ts`, `csv.ts`; `@todo/data` `import-apply.ts`): files are untrusted input. Parse with Zod against the database's own limits, skip bad items with a warning (never silently), remap every id, and go through `planImport`. Importing writes in batches, rolls back (soft-deletes what it created) on failure, and returns an undo. CSV export prefixes `= + - @` cells with an apostrophe against formula injection and import strips it. The JSON format is versioned (`todo-export`, version 1); change it only with a new version.
- Playwright: `getByRole("alert")` also matches Next's invisible route announcer; scope alerts to a region.
- Offline (M4): the browser Supabase client's `fetch` is `createOfflineFetch` (`@todo/data` `offline-fetch.ts`, wired in `apps/web/src/lib/supabase/client.ts`). A write that cannot reach the server is stored in `localStorage` (`todo-offline-writes`, tied to the user) and answered as saved, so the hooks stay unchanged; the queue replays in order on `online` (and at start), a read waits for it, a 409 on a primary key counts as already done, other 4xx are dropped with a toast. Writes that ask for rows back (`.select()` after a write) and rpc calls are not queued, so anything that must work offline is a plain insert/update/upsert with client-made ids. Conflicts are last-write-wins; before replaying, edits made offline are checked once against `updated_at` and a toast says when a row changed elsewhere meanwhile.
- The query cache is saved to IndexedDB (`todo-query-cache`) through `lib/persist-codec.ts` (JSON would turn `Date`s into strings) and is refetched right after it is restored; keep local form state in sync with the task (see `Drawer`). `OfflineAwareQueryClient` stops mutations waiting on refetches while offline. Signing out goes through `signOut` in `lib/offline.ts` (asks before dropping unsent edits).
- PWA: `public/sw.js` (production only; caches `/_next/static` and visited pages, never Supabase), `app/manifest.ts`, `app/icon.tsx`. `proxy.ts` must keep letting `/sw.js`, `/manifest.webmanifest` and `/icon/*` through without a session. Realtime (`lib/realtime.ts`) needs the tables in the `supabase_realtime` publication (migration `20261021090000_realtime.sql`; apply it to the hosted project before relying on live updates there).
- `next build` bakes `NEXT_PUBLIC_*` in from `.env.local` (the hosted project). For `E2E_SERVER=start` run `pnpm --filter @todo/web build:e2e` first (it uses the local address); `playwright.config.ts` refuses to run if the build does not contain the local URL.
- Mobile (M5, `apps/mobile`, Expo 58 + expo-router, Expo Go compatible): `src/lib/polyfills.ts` must be the first import (SQLite-backed `localStorage` and `crypto.randomUUID`); the session, offline queue and saved cache all live in that `localStorage`. Same design as web: `getBackend()` builds the client with `createOfflineFetch`, `components/providers.tsx` mirrors the web providers (NetInfo feeds TanStack's `onlineManager`), screens are thin and call `@todo/data` hooks plus `selectView`. Swipe rows (`swipe-row.tsx`, PanResponder, no native gesture library) are only a shortcut: every swipe action must also be an accessibility action. Needs `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (`apps/mobile/.env.example`; a phone needs the computer's LAN address for local Supabase). Never test against the hosted project. `pnpm --filter @todo/mobile build` bundles Android (a quick compile check); Maestro flows are in `.maestro/` and need a built app; builds go through `eas.json`. App ids are `com.cjgdizon.todo`; they cannot change once published. Push: `push_tokens` is written only through `register_push_token` / `unregister_push_token` (a device moves to whoever signs in on it); `lib/push.ts` needs an EAS project id (`eas init`) and a development build, it silently does nothing in Expo Go. Migration `20261024090000_push_tokens.sql` is local only until applied to the hosted project. Mobile task screen (`app/task/[id].tsx`) has reminder, assignee, timer and comment sections (components of the same names); mobile has no realtime yet, so other people's changes show after a refetch, and no attachments screen yet. The More tab (`app/(tabs)/more.tsx`) has the workspace switcher, members with invite codes (`members-section`; mobile shares the code, not a link, because it has no web address; `join-section` accepts a pasted code or link through `inviteTokenFrom` in `@todo/core`), weekly stats (`useStats`) and activity.
- Collaboration (M6): people join only through invites. `create_workspace_invite` returns a token once and stores its SHA-256; `accept_workspace_invite` is the only way in; both are rpc calls, so they are never queued offline. The invite link is `/join?token=...`; `safeNext` (`apps/web/src/lib/safe-next.ts`) is an allow-list of exactly that path, so the sign-in redirect (`/login?next=`) cannot become an open redirect, and `/auth/callback` still ignores `next` (magic-link users reopen the invite link after signing in). The active workspace is a per-user preference in `localStorage` (`lib/active-workspace.ts`); `useBootstrap(client, userId, preferredId)` falls back to the oldest workspace. Members, invites and comments hooks are in `@todo/data` `collab-hooks.ts`; assigning is `useUpdateTask({ assigneeId })`. The two-user flow is covered by `e2e/collaboration.spec.ts`. Activity feed: `activity_log` is written only by triggers (`20261026090000_activity_log_triggers.sql`; clients have select only), and only while a workspace has two or more members; comment text is never copied into it; `purge_deleted` also drops entries older than 180 days. `describeActivity` (`@todo/data`) words the lines for web and mobile. Mentions: the app finds `@Name` in a comment (`findMentions` / `splitMentions` in `@todo/core`: @ at the start of a word, whole display name, longest name wins, case ignored; identical display names are ambiguous and the first match wins) and sends the ids in `comments.mentions`; the database keeps only members of the workspace (max 20) and logs a `mentioned` activity line per person other than the author. Editing a comment re-filters its mentions but does not log new ones, and mentions send no push yet. Reminders (M6 B): a reminder is "N minutes before due" for one person; clients only call `set_task_reminder` / `clear_task_reminder` (rpc, so online only), the database computes `remind_at` (all-day tasks count as 09:00 local) and re-arms it when the task is rescheduled. The `send-reminders` Edge Function (`supabase/functions/send-reminders`, `verify_jwt = false`, checks `x-cron-secret` against `REMINDERS_CRON_SECRET`, fails closed) is called every minute by a pg_cron job that reads its URL and secret from Vault (`reminders_function_url`, `reminders_cron_secret`); it claims due rows with `claim_due_reminders` (service role only; marks them sent, so each fires at most once), pushes through Expo and forgets dead tokens. A person keeps at most their 10 newest devices (`register_push_token` trims, `claim_due_reminders` also caps) so one account cannot fan notifications out; task titles are sent to Expo's push service and the phone makers' (Apple/Google) as the notification text; generate `REMINDERS_CRON_SECRET` with at least 32 random bytes (`openssl rand -hex 32`). Message building and Expo receipt parsing are in `@todo/core` `reminders.ts`. Locally: `supabase functions serve send-reminders --env-file <file>` with `REMINDERS_CRON_SECRET` (and `EXPO_PUSH_URL` to point at a stand-in). Time tracking and stats (M6 C): timers are plain `time_entries` writes with client-made ids and times (offline-safe); the database allows one running timer per person, so starting one stops the running one first (`useStartTimer`). A focus session (Pomodoro) is a timer plus an end time kept in `localStorage` (`lib/focus.ts`); the `RunningTimer` bar in the app shell ends it. Stats (`@todo/core` `stats.ts`) read `tasks.completed_at` and `time_entries`; nothing writes `task_completions`, so advancing a repeating task is not counted. Attachments (M6 C): files live in the private `attachments` Storage bucket under `<task id>/<attachment id>-<safe name>` (`attachmentPath` in `@todo/core`; 10 MB limit enforced by the bucket and `validateAttachment`); access follows `private.can_access_attachment_path` / `can_delete_attachment_path` (workspace members read and add, only the uploader or an admin removes), tested in db-tests and checked against real Storage. Upload stores the file first, then the `attachments` row (and removes the file if the row fails); downloads are 60-second signed links with `download`, never inline. Nothing yet removes the files of purged attachment rows from Storage (`purge_deleted` only drops rows). Migrations `20261024100000_workspace_invites.sql`, `20261026090000_activity_log_triggers.sql`, `20261026100000_reminders.sql`, `20261026110000_attachments_storage.sql` and `20261027090000_comment_mentions.sql` are local only until applied to the hosted project.
- Views are pure functions of the task list (`selectView` in `@todo/data`, `dueBucket`, `groupUpcoming`, `buildTaskTree`, `planCompletion` in core). Writes go through the `@todo/data` hooks so they stay optimistic and undoable.
- Never write a `\uXXXX` escape through the editing tools: it is converted to the literal character. Build such strings from character codes.
- Secrets never in client code or git. Google refresh tokens live in Supabase Vault, server-side only.
- Google Calendar sync is opt-in; `calendar_integrations.enabled` is checked first by every `gcal-*` function. Built so far (M6b): the mapping (`@todo/core` `calendar-sync.ts`: a task is an event only while it has a due date and is neither done nor deleted; a cancelled event removes the due date, never the task; events with no linked task are ignored, so the calendar is not turned into a task list) and the engine (`calendar-engine.ts`: `pushTask` / `pullChanges` over injected `CalendarPort` and `TaskStorePort`, tested with in-memory fakes; changes cannot bounce thanks to `task_calendar_links.last_synced_version` and the stored etag; both sides editing the same item before a sync is last-writer-wins). Tables (`20261027100000_calendar_sync_schema.sql`): clients read their own status only, the token reference and sync cursor are column-hidden, deleting an integration deletes its Vault secret, and `calendar_sync_queue` (filled by a trigger on task changes, server-only) is what the `gcal-sync` function drains. The `gcal-sync` Edge Function (`supabase/functions/gcal-sync`, `verify_jwt = false`, checks `x-cron-secret` against `GCAL_CRON_SECRET`, fails closed) is called every minute by a pg_cron job (Vault secrets `gcal_sync_function_url`, `gcal_cron_secret`; migration `20261027110000_calendar_vault.sql`): per enabled person it takes their queued tasks (failures are put back), pushes them, then pulls Google's changes by sync token (polling, no webhook yet). Google calls live only in `functions/_shared/google.ts` (every address overridable by env for tests); the refresh token is read and written only through service-role SQL helpers (`save_calendar_connection`, `get_calendar_refresh_token`, `disconnect_calendar`). `node scripts/gcal-check/check.mjs` runs the real function against a stand-in Google (`mock-google.mjs`) and the local database through the whole scenario (needs Docker and `pnpm db:start`). `gcal-connect` (POST from the app: verified login + workspace membership, returns the consent address with a signed `state` from `@todo/core` `oauth-state.ts`; GET from Google: no login, so the state is the only credential, 10-minute expiry; the browser is returned only to `GCAL_RETURN_URL`, never an address from the request; CORS only for that origin) creates the dedicated Tasks calendar and calls `save_calendar_connection`; `gcal-disconnect` (keep or remove the events; always disconnects, deletes the Vault token). The scope is `calendar.app.created` (only calendars this app created); if Google refuses an operation with a real account, check that first. The settings sections are `calendar-settings.tsx` (web) and `calendar-section.tsx` (mobile More tab; Google returns to the web settings page). Needed to go live (set as Edge Function secrets, never in git): `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GCAL_STATE_SECRET` (32+ random bytes), `GCAL_CRON_SECRET`, `GCAL_RETURN_URL` (the web settings address), `GCAL_REDIRECT_URI` (the `gcal-connect` function address, also registered in the Google Cloud OAuth client), plus Vault entries `gcal_sync_function_url` and `gcal_cron_secret`. Not built: webhooks (changes in Google are polled each minute), importing events made in Google.
